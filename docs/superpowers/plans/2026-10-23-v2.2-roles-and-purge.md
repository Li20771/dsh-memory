## 1. 先确认一件事：分段问题解决了

你说"一个工作区理论上只有一个大项目"。所以上一轮我问的"能否多活跃段"答案是**不能，也不需要**：

```
一个工作区 = 一个大项目 = 一个活跃段（ep）
项目完成 → 收割 → 销毁 → 该工作区可开新段
```

`ws_<id>` 下永远最多一个 `active` 段。多段逻辑全部删除，实现变简单了。

**这也让"生命周期"和"工作区生命周期"几乎重合** —— 除了一个例外：项目完成后工作区还在（要开下一段），而删除工作区是连根拔。

## 2. 角色模型：协调会话 / 作业会话

### 2.1 两角色

| | **协调会话**（Coordinator，你的"特殊会话"） | **作业会话**（Worker） |
|---|---|---|
| 数量 | 1 个或多个 | 多个 |
| 职责 | 项目前调研与规划；进行中遇阻时改进规划；**按角色把任务分给作业会话**；审查产出；裁决记忆 | 执行被分派的任务；**可读全工作区记忆**；写入自己的产出与观察 |
| 生命周期 | 贯穿整个段 | 任务级（可短可长） |
| 典型交互 | 你直接和它讨论 | 你或协调会话发起 |

### 2.2 派活：复用 DSH 原生原语，不造新轮子

DSH 已经有三件套，正好够用：

| 需求 | 现成能力 |
|---|---|
| 建任务、按角色分派 | `team_task_create` / `team_task_list` / `team_task_update`（共享任务板） |
| 会话间通信（派活、回报、追问） | `send_message`（可发给任意 teammate/会话） |
| 会话内并行子任务 | `subagent` / `subagent_fork` |

所以**协调会话不发明调度层**，它只是：有权限创建任务、有权限审查结果的会话。这大幅降低实现风险。

### 2.3 权限矩阵（这是本设计的核心）

| 操作 | 协调会话 | 作业会话 | 依据 |
|---|---|---|---|
| 读 L4 全部（含他人的产出） | ✔ | ✔ | 你明确要求"接受任务的会话也要能查看" |
| 写"事实/观察"记忆 | ✔ | ✔ | |
| 写"规划/任务分配"记忆 | ✔ | ✘ | 只有协调会话能定义"该做什么" |
| 修改他人记忆的正文 | ✔（留原值 + 修订者 + 时间） | ✘（只能提交建议） | `arXiv:2608.01679` 权限坍缩 |
| 标记 `superseded` / `retracted` | ✔ | ✘ | |
| 审查（approve / revise / reject） | ✔ | ✘ | |
| 发起收割 | ✔ | ✘ | v2.1 N1：只有人/协调者能发起 |
| 提升到 L1 / L3 / KB | ✔ | ✘ | |
| 读 `sensitivity: sensitive` | ✘ | ✘ | 谁都不能自动进上下文 |

**作业会话"能写不能改别人的"**，这是防污染扩散的关键。理由：如果作业 A 能改写作业 B 的记忆，一次误判就能污染整个项目；而 `arXiv:2609.30813` 证明——**一个无争议的假信念进库后，下游会话在 0.97–0.99 的探测里都会断言它**。

### 2.4 审查状态是记忆的一等字段

```yaml
review:
  state: pending        # pending | approved | revised | rejected
  by: sess_coord_ab12
  at: 2026-10-23T10:20:00+08:00
  note: "结论对，但适用条件写窄了"
  originalTextSha: 9c31...   # revised 时保留原值指纹
```

规则：
- 作业会话写入 → `state: pending`
- 协调会话审查 → `approved` / `revised`（含修订正文 + 原值指纹）/ `rejected`
- **召回时 `pending` 降权并显式标注**（不是隐藏——隐藏会让作业会话"看不到自己刚写的"，很困惑）

这是 `arXiv:2610.11188`（admission vs presentation）的落地：**准入不拒，呈现时降权并声明状态**。

## 3. 一件必须说清的事：角色是"声明"，不是"证明"

**这是本设计最重要的一处诚实边界。**

问题：作业会话能不能自称协调会话？

- 如果角色由 agent 自己通过工具设置 → **任何会话都能提权**，权限矩阵形同虚设。
- 如果角色由密码学令牌签发 → 需要服务端，DSH 单机没有这个边界。

**我的方案**：角色**由你（用户）声明**，写在**工作区标记文件**里：

```json
{
  "schema": 1,
  "enabled": true,
  "id": "ws_securitylab",
  "episode": "ep_2026_10_cpa",
  "coordinators": ["sess_coord_ab12"],
  "activeCoordinators": ["sess_coord_ab12"]
}
```

插件只做两件事：
1. **强制一致性**——不在 `coordinators` 列表里的会话，一律按 worker 权限处理（fail closed）
2. **留痕**——角色变更写 journal

**它不保证什么**：
- 不防"agent 有文件写权限、自己去改 marker 文件"。这需要 OS 级沙箱或服务端，不在本轮范围。
- 所以这是**协作式授权（cooperative authority）**：防误用、防遗忘、防手滑，**不防蓄意攻击**。

我把这条写进设计而不是藏着，因为 `arXiv:2608.01679` 的教训正是"**系统暗示了比它实际拥有的更高权限**"就是 authority collapse。我们自己的设计不能犯同一个错。

## 4. UI 按钮：可行，但我不打算现在做

### 4.1 可行性判定（已查证）

| 事实 | 证据 |
|---|---|
| client 插件面存在 | `dsh-plugin-wallpaper-engine` 是活的先例：`package.json` 里 `dsh.client` = `{platform:'web', inject:[...]}`，`exports["./client"]` 指向 `lib/client.js` |
| 有 UI 插槽机制 | `dsh-client-ui-session/README.zh.md`："通过**标准 Slot 钩子**公开 Session catalog…"，并提到 "Slot scope" |
| **但 slots 包不在 node_modules** | `@deepseek-ai/dsh-client-ui-slots`、`dsh-client-runtime` 均**不存在于磁盘** |
| 那它从哪来 | `dsh-client-modules` 文档：外壳初始化**一张冻结的模块表 `PLATFORM_MODULES`**，浏览器 bundle 针对该基座解析 external → **它是浏览器侧平台模块，不是 node 包** |
| 会话创建能力 | `dsh-api-session-controller` 导出 `SessionController`，可编程管理会话 |

**结论**：加按钮**在技术上可行**，走 wallpaper-engine 那条路（独立 client bundle + `pnpm run build`）。

### 4.2 但为什么我建议延后

1. **无法在 host 侧验证**：client bundle 要在真实浏览器 + HMR 里跑，测试成本远高于 host 插件。
2. **插槽 id 未确认**：我还不知道"新建会话栏"对应哪个 slot。这需要读 `dsh-client-ui-session/lib/client.js`（40KB）做插槽考古。
3. **它是体验优化，不是能力前提**：角色模型完全可以先跑起来。

### 4.3 降级路径（建议先做这个）

**Host-first**：先把角色与权限做成 host 侧概念，用三种方式声明协调会话（不需要 UI）：

```
方式 1（最简单）：在你给协调会话的第一条消息里说"这是本项目的协调会话"
                 → 插件识别并写入 marker 的 coordinators
方式 2：一个工具 workspace_role(action: claim-coordinator | list | release)
方式 3：直接编辑 .dsh/memory.json（永远可用的后门）
```

等 UI 插槽确认了，再把"方式 1/2"换成按钮——**底层权限模型不变，只换取入口**。

这是我建议的次序：**先有正确的权限模型，再有好看的入口**。

## 5. 清除规则：两种触发

| 触发 | 场景 | 行为 |
|---|---|---|
| **A. 项目完成收割** | 工作区保留，开下一段 | `active → harvesting → closing(冷静期 7d) → purged`；工作区文件不动；可以开新段 |
| **B. 主动删除工作区** | 这工作区不要了 | 段直接进 `closing`，**跳过 harvesting**，附**墓碑**列出"未收割条目数"；工作区目录若被删则 marker 一并消失 |

**B 的设计要点**：
- **不静默**：删除前若存在 `pending` 或未收割条目，先给你一份清单（"有 12 条记忆未处理，其中 3 条看起来是重要结论"），你确认才继续。
- **仍走回收站**：即使你删了工作区，L4 记忆本体进 `.trash/` 保留 7 天——因为工作区文件可能还在回收站，记忆也可能要捞回来。7 天后物理删。
- **墓碑必须写**：`journal.jsonl` 记 `op: purge-workspace, ws, ep, reason, unharvested_count`。因为**"曾经有过这个项目"这件事本身是有价值的元信息**，而内容必须消失。

## 6. 新增风险（5 条）

| # | 风险 | 说明 | 应对 | 状态 |
|---|---|---|---|---|
| R1 | **角色自封（提权）** | 作业会话把自己写成协调会话 | marker 白名单 + fail closed（非白名单一律 worker） | 🟡 **协作式**，不防蓄意改文件 |
| R2 | **审查滞后** | 协调会话没审，作业会话已基于 `pending` 记忆继续干 | `pending` **降权 + 显式标注**；协调会话可批量审查；关键操作（写 L3/KB）强制要求 `approved` | 🟡 部分 |
| R3 | **多协调者冲突** | 你说可以有多个协调会话 → 可能给出互斥决定 | 决策**只追加不覆盖**，冲突以 `conflict` 标记浮出，不静默取一个 | ✅ 可机械检测 |
| R4 | **协调会话成为单点** | 它挂了/上下文爆了，整个项目停摆 | 协调会话本身是普通会话，可随时新开并接管（marker 里换 id）；L4 是共享状态载体，不依赖某个会话存活 | ✅ 设计已保证 |
| R5 | **共享读导致污染扩散** | 作业 A 的错误观察被作业 B 当真 | 已有的 `authority` + 来源族去重 + `pending` 降权；再加：**跨会话引用必须带原始 id**，不许转述 | 🟡 部分 |

**R2 值得展开**：这是多会话协同里最隐蔽的坑。协调会话可能几小时才审一次，而这期间 5 个作业会话已经把一条错记忆当事实用了 20 次。所以：
- `pending` 记忆**可以读，但注入时明确标注"未经审查"**
- **升级动作（写 L3、写 KB 结论、标记 done）要求 `approved`**
- 协调会话审查时可以**批量**（按时间窗或按任务 id）
