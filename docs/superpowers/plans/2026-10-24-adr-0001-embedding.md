# ADR-0001：是否引入 embedding

> 日期：2026-10-24　｜　状态：**accepted（已采纳并实现）**
> 背景决策：设计 v3 §D5「基线不做 embedding」——**本 ADR 修正其"完全不做"，改为"默认不做，可选扩召回"**

---

## 1. 背景

P5 收尾时确认的硬缺口：**纯概念断言会漏选**——没有数字、没有标识符、只有同义改写的句子，靠词元与锚点匹配抓不到。这是 D5 的直接代价。

现在问：能不能把 embedding 引进来补这个缺口？

**先纠正一个我自己早前说过头的限制。** 我之前说"插件不能有任何第三方依赖"，理由是 profile 的 `node_modules/@deepseek-ai` 是空目录。这句话只对 SDK 包成立——**插件自己的 `plugin/node_modules/` 是能被 Node 正常解析的**。所以"技术上不能装依赖"是错的；真正的约束是**可迁移性与运行环境**，不是模块解析。

---

## 2. 三种引入方式

| 方式 | 做法 | 体积/依赖 | 可迁移性 |
|---|---|---|---|
| **A. 外部 HTTP 服务** | 调 `/v1/embeddings`（本机已有一个在 `127.0.0.1:8001`） | 0 安装 | ❌ 换机器服务不在就降级 |
| **B. 内置 ONNX + 小模型** | vendored `onnxruntime-node` + `bge-small-zh`(~100MB) | ~200MB + 原生二进制 | ❌ 原生二进制绑平台/Node ABI |
| **C. 纯 JS 哈希向量** | token 计数做随机投影 | 0 | ✅ | **但它不是语义的**，等价于把 bag-of-words 换个表示——对缺口毫无帮助，只是自欺 |

C 可以直接排除。真正的选择是 A 或 B。

---

## 3. 引入 embedding 的缺陷（七条，按严重度）

### ① 可迁移性被击穿（最严重）
模型或服务是**本机资产**，记忆仓库里不含它。clone 到另一台机器：要么重下 100MB+，要么服务不可达。**召回行为在两台机器上不一样**——而 P6 的目标恰恰是"clone 下来就能用"。这跟 D4 直接冲突。

### ② 跨作用域泄漏面回来了
`arXiv:2610.04195`（MemLeak）的根因就是**共享嵌入空间**：语义相邻的条目会跨作用域被召回，且**无需任何利用**，普通余弦检索即可，实测非对抗泄漏 70–100%。

我现在靠"关键词 + scope 过滤 + 无共享空间"天然隔离。加了向量后，**必须为每个 scope 单独建向量索引**，物理上不共享。一旦为了省事共用一个索引，工作区隔离就被语义相似性击穿。

### ③ 隐私边界扩大
算向量要把**笔记内容**送出去。用外部 API = 把安全研究笔记发出去；用本地模型 = 模型文件与向量缓存落盘都是本机资产。两者都扩大了暴露面。

### ④ 向量相似度不是质量信号
`arXiv:2610.26433` 实测：用嵌入几何预测答案正确性，pooled AUROC **0.640**，**低于"问题难度"基线 0.655**；控制难度与系统身份后几何特征的增益进一步消失。

结论很直接：**向量能把"看起来相关"的东西捞上来，但不代表它支撑断言**。加它不是"变好"，而是**把失败模式换个样子**——从"漏选"变成"选中语义相近但事实相反的那句"。后者更危险，因为它看起来像证据。

### ⑤ 成本与延迟
MemoryTax（`arXiv:2610.29823`）的核心批评："设计好的记忆是弱模型的昂贵补丁"。写入路径要算向量 → 必须异步/批处理，复杂度上升；查询路径要算一次 query 向量，本地小模型 ~10–50ms 可接受，外部 API 则是网络抖动。

### ⑥ 可解释性下降
现在每条召回能说清"命中哪些词、哪些锚点"。向量相似度说不出原因——**出问题时无法归因**，而这套东西的全部价值就在"可复核"。

### ⑦ 运维负担
原生模块要跟 Node ABI 对齐（本机 Node 24），Windows + 特定版本是真实的坑；模型版本升级会让旧向量失效，需要全库重算。

---

## 4. 但缺口是真的

不引入，就永远抓不到"无锚点的同义改写"。这是真实损失，不能假装不存在。

---

## 5. 提案：引入，但只让它做"扩召回"，不让它做"排序"

```
query ──[向量]──▶ 候选 N×3（宽召回）
                     │
                     ▼
              现有可解释打分（IDF + 锚点 + recency + salience）
                     │
                     ▼
                  top-k 注入
```

三条设计约束：

1. **向量只扩大候选集，不决定最终排序。** 直接对冲缺陷 ④：很像但不支撑的句子会被后续可解释打分压下去，而漏选被补上。
2. **向量索引按 scope 物理分片。** 直接消掉缺陷 ②：工作区/项目各自独立，永不跨片检索。
3. **provider 可插拔 + 默认关闭 + 失败即降级。** 服务不可达时**静默回落到纯关键词**，并在 `memory_diagnose` 里报"语义扩展未启用"。这样缺陷 ① 从"坏掉"降级为"少一点召回"，不会让系统不可用。

实现顺序建议：
- **先做 A（HTTP provider）**：零安装、立刻可验证，用本机已有端点。接口定成 `{ embed(texts: string[]) => Promise<number[][]> }`，将来换成本地模型不动上层。
- **本地模型（B）只在你明确要求"完全离线"时再做**，并且接受它不做仓库的一部分。

配套：向量缓存放在 `.kb-index/`（gitignored，可重建），**不进记忆仓库**——保证仓库本身仍然可迁移。

---

## 6. 决定

**采纳提案**（判据：把"是否比不引入更好"逐维度比较）。

| 维度 | 不引入 | 提案 | 胜 |
|---|---|---|---|
| 纯同义改写漏选 | ❌ 永久缺口 | ✅ 扩召回补上 | **提案** |
| 排序质量 | 可解释、可归因 | **不变**（向量不参与排序） | 平 |
| 跨作用域泄漏 | 无 | 分片后仍无 | 平 |
| 可迁移性 | 完好 | 默认关 + 失败降级 → 最坏退回现状 | 平 |
| 回归风险 | — | 默认 OFF，行为逐字节一致 | 平 |
| 复杂度 | 一个文件不多 | 多一个 provider + 缓存 | 提案略亏 |

**结论：只有复杂度变差，而这换掉的是唯一一个我自己补不上的缺口。** 因此采纳。

实现已于 2026-10-24 落地：`plugin/lib/vault/embedding.js`（provider + 分片 + 失败降级）、`query.js` 的 `candidateBoost`（扩召回不排序）、`memory_diagnose` 报 provider 状态。13 项新测试覆盖默认关闭、失败不抛、分片隔离、boost 不影响排序。

**部署方式**：默认 `embedding.enabled = false`。要开启，在 profile 的 `cordis.patch.yml` 里给 `dsh-memory` 加 config：

```yaml
- id: dsh-memory
  config:
    embedding:
      enabled: true
      endpoint: http://127.0.0.1:8001/v1/embeddings
      model: your-embedding-model
```

## 7. 后果（无论选哪个都成立的部分）

- 默认关闭时，行为与现在**完全一致**，无回归风险。
- 一旦开启，`memory_diagnose` 必须显示"语义扩展: 开/关 + provider"，否则用户无法判断召回为什么变了。
- 向量索引**永不进仓库**。这条不接受妥协。
