## 1. L4 重新定义

你这句话改变了 L4 的性质，不是调整参数：

> 工作区记忆是为了增强单个工作区内会话的继承和协同，这个记忆是暂时性的，只在项目进行时有用，完成后得到成果（项目成果、工作流、录入知识库）后即销毁。

**从"长期累积的记忆"→"有生命周期的会话期记忆（Episode Memory）"。**

### 1.1 命名与作用域

| | 值 |
|---|---|
| 名称 | L4 会话期记忆（Episode Memory） |
| 读作用域 | `ws_<id>`（工作区内所有会话可读，符合你说的"本工作区所有会话"） |
| 分段单位 | `ep_<id>`（一个项目周期一段；销毁以**段**为单位，不整库销毁） |
| 存活期 | 段打开 → 项目进行中 → 收割 → 销毁 |

**待你确认的一处理解**：你既说"本工作区所有会话共享"，又说"项目完成后销毁"。我按"**工作区作用域 + 分段生命周期**"实现：同工作区可同时有多段（多个并行项目），会话读取本工作区所有**活跃段**；某段关闭时只销毁该段，其他段不受影响。若你要的是"工作区只能有一个活跃段"，说一声，实现更简单。

### 1.2 生命周期状态机

```
open ──▶ active ──▶ harvesting ──▶ closing ──▶ purged
  │         │            │             │
  └─────────┴────────────┴────────────▶ abandoned（长期停滞 → 要么续、要么收割、要么弃）
```

| 状态 | 含义 | 可写 | 可读 | 触发者 |
|---|---|---|---|---|
| `open` | 段已创建，尚未有实质内容 | ✔ | ✔ | 会话首次写入 |
| `active` | 正常运行 | ✔ | ✔ | — |
| `harvesting` | 正在收割，**冻结写入** | ✘ | ✔ | **人**发起 |
| `closing` | 收割已验收，冷静期中 | ✘ | ✘ | 人确认 |
| `purged` | 已销毁，仅留墓碑 | ✘ | ✘ | 冷静期满 |
| `abandoned` | 主动放弃（不收割，直接销毁） | ✘ | ✘ | 人显式 |

**关键约束：`harvesting` 之后一律不可写。** 否则收割过程中新写入的内容会漏掉，形成"以为收割完了其实没有"。

### 1.3 收割契约：三出口 + 全覆盖检查

你说成果有三个去向：**项目成果 / 工作流(L3) / 知识库(KB)**。所以收割是**三出口**，且必须满足**全覆盖**：

> L4 段内的每一条记忆，必须落到且仅落到以下三种处置之一：
> 1. `harvested` → 指向它被写入的产物（`kb/...` 或 `workflows/...`）
> 2. `discarded` → 附**理由**（噪声/一次性/已被取代）
> 3. `deferred` → 明确转入长期记忆（少数确实该跨项目的）
>
> **不允许"未处理"。** 这是唯一可机械验证的收割质量保证。

实现：`harvest_report.json` 列出每条 id + 处置 + 目标 + 处置时间。一条 `active` 记忆在 `harvesting` 状态下没出现在报告里 → **拒绝进入 `closing`**。

这是我对 `arXiv:2610.18052`（Bemula，记忆遗忘基准）的借鉴——它的验收标准是"**精确删掉被要求删的，同时保持其余记忆完整**"，我要的是对偶：**精确移交该移交的，同时不丢任何一条**。

## 2. 文献支持：你的直觉撞上了 5 天前的论文

**`arXiv:2610.25561`《Let Them Sleep: Recursive Self-Pruning Memory for Long-Horizon LLM Agents》**（2026-10-18）：

> 存下每条轨迹、检索最近邻，**早期好用，之后会安静地失效**：存储被"agent 随后会重复的失败"和"五十轮前才成立的事实"填满。
> RSPM 借用生物学的解法：**定期"睡眠"——把最近的失败聚类，每簇蒸馏成一条短规则，然后删掉刚学过的原始片段。规则不被强化就衰减；跨多个上下文反复出现的规则被提升为通用规则。**

这几乎是你在描述的机制的完整版。它比我原方案多两个我没设计的东西，我建议直接吸收：

1. **规则衰减** —— 蒸馏出的 L3 工作流若无后续强化会衰减。防止"一次性经验永久晋升为流程"。
2. **跨上下文复发才提升** —— 已经是我的 family 去重思路，RSPM 补上了"衰减"这一半。

配套证据（用于给"收割后该不该进 L3"设门槛）：
**`arXiv:2610.18427`《Reliable Memory from Unstable Growth》** —— 决定一条自写教训是否真的改善后续任务时，用**随机对照试验**而不是"看起来有道理"。→ 收割进 L3 的候选应标注"未经 A/B 验证"，避免经验噪声升格为流程。

## 3. 销毁半径：一个我不打算假装能解决的问题

**`arXiv:2610.17659`** 明确指出：*参数级遗忘不够——**遗忘的信息可能仍存在于记忆工件中**，或被重新唤起。*

"销毁 L4"这句话在技术上必须拆成**五个残留面**，它们能不能清、代价多大，差别巨大：

| # | 残留面 | 能否清除 | 我的处置 |
|---|---|---|---|
| 1 | 派生索引 `.kb-index/` | ✅ 完全可清 | 直接重建；`purge-index` 必做 |
| 2 | 记忆文件本体 | ✅ 可清 | 移入 `.trash/`，冷静期 7 天后物理删 |
| 3 | `journal.jsonl` 审计尾 | 🟡 只追加不可删 | 写**墓碑行**（`op:purge, segment, manifest_sha`），保留"曾存在过什么类型的段"，不保留内容 |
| 4 | **git 历史** | ❌ **物理上清不掉** | **只能靠"敏感内容一开始就不进 L4"**。git 历史不可改写 |
| 5 | **已注入会话上下文的消息 + 模型 KV 缓存** | ❌ **清不掉** | 只能靠"段结束时提醒用户该会话已无价值"；KV 缓存不可控 |

**第 4 条是硬约束，它反过来约束决策 5（敏感度）：**

> 一旦敏感内容进入了 L4 的文件层，它就进了 git 历史，**永久不可销毁**。

所以敏感度字段不能只是"过滤"，必须升级为**写入闸门**：

```
sensitivity: sensitive → 禁止写入 L4 持久层（只能存在于当前会话上下文）
sensitivity: normal    → 正常写入
```

否则"用完即销毁"对敏感内容是**假的**。

**第 5 条我也要明说**：销毁之后，**已经把它注入过的那个会话的上下文里仍然有它**。这是架构决定的，不是 bug。
